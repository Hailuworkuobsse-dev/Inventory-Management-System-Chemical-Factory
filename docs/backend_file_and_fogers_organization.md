# Backend Folder & File Organization – AIMS

A *production‑ready, full‑stack* backend that meets all 90 functional requirements, the database design, and the API contract. The structure follows a **modular (feature‑based) architecture** with clear separation of concerns, making the codebase maintainable, testable, and scalable.

---

## Root Directory Layout

```
backend/
├── prisma/                       # ORM schema & migrations
├── src/                          # Application source code
│   ├── modules/                  # Feature modules (core business domains)
│   ├── middleware/                # Reusable Express middlewares
│   ├── utils/                     # Shared utilities, custom errors, Prisma singleton
│   ├── config/                    # Environment, DB, CORS, and other configurations
│   ├── services/                  # Cross‑cutting services (audit, notifications, integrations)
│   ├── jobs/                      # Background jobs, scheduled tasks
│   ├── app.js                     # Express app setup, global middlewares, route mounting
│   └── server.js                  # Entry point – starts HTTP server, DB connection, MQTT client
├── tests/                         # Unit, integration, and e2e tests
├── .env / .env.example
├── package.json
├── Dockerfile
└── docker-compose.yml
```

## Detailed Breakdown

### 1. `prisma/`
- `schema.prisma` – the complete data model (already provided).
- `migrations/` – auto‑generated by `prisma migrate`.

### 2. `src/config/`
Centralises all environment‑dependent settings.

| File               | Purpose |
|--------------------|---------|
| `index.js`         | Loads and exports all configuration from `.env` (port, JWT secrets, DB URL, MQTT broker, eRIS endpoints, etc.). |
| `database.js`      | (Optional) Additional DB‑specific settings, like connection pool limits. |
| `corsOptions.js`   | CORS configuration reused by the `cors` middleware. |

---

### 3. `src/middleware/`
Every request passes through these before reaching a controller.

| Middleware             | Responsibility                                            |
|------------------------|------------------------------------------------------------|
| `authMiddleware.js`    | Verifies JWT access token, attaches `req.user`.           |
| `rbacMiddleware.js`    | Role‑based access control – checks required permissions.   |
| `validate.js`          | Generic validation middleware (e.g., using Joi/Zod schemas). |
| `errorHandler.js`      | Global error handler that formats all errors consistently. |
| `requestLogger.js`     | Logs every request (method, URL, response time).          |

---

### 4. `src/utils/`
Shared tools and helpers.

| File                 | Purpose |
|----------------------|---------|
| `prisma.js`          | Singleton Prisma client instance used by all services. |
| `appError.js`        | Custom error class with statusCode, message, and operational flag. |
| `responseHandler.js` | Helper functions for standardised JSON responses (`successResponse`, `errorResponse`). |
| `emailSender.js`     | Wrapper for alert emails (FR‑061). |
| `pagination.js`      | Standardise pagination parameters from query strings. |

#### Typical module file details
**Controller:** thin layer, calls service, sends response.  
**Service:** contains **all business logic**, database calls (via `prismaClient`), and coordinates with external integrations.  
**Routes:** mounts the module's endpoints with appropriate middleware (`authMiddleware`, `rbacMiddleware`, `validate`).  
**Validation:** defines request schemas (using Joi or Zod) for each endpoint.

### 6. `src/services/` (Cross‑cutting)
Services that are used across multiple modules.

| Service                     | Purpose |
|-----------------------------|---------|
| `audit.service.js`          | Centralised function to log any entity change into `AuditLog` (called from every module's service). |
| `notification.service.js`   | Push notifications (WebSocket/SSE) and email/SMS for expiry, stock‑out, recalls. |
| `integration/eris.service.js`     | Formats data and exports for EFDA's eRIS system (FR‑002). |
| `integration/erp.service.js`      | Bi‑directional sync with external ERP (FR‑078). |
| `integration/mqttClient.js`       | MQTT client that subscribes to IoT topics and calls `iot.service` on incoming readings. |
| `integration/forex.service.js`    | Pulls/updates exchange rates from NBE or manual source. |

---

### 7. `src/jobs/` (Scheduled Tasks)
Background jobs run via a scheduler (node‑cron, BullMQ) to perform periodic operations.

| Job                    | Trigger         | Purpose (FR)                                |
|------------------------|-----------------|---------------------------------------------|
| `expiryAlertJob.js`    | Daily at 08:00  | Checks batches expiring in 30/60/90 days and creates alerts (FR‑013). |
| `stockOutRiskJob.js`   | Every 6 hours   | Compares stock vs. safety stock, flags critical medicines (FR‑061). |
| `abcAnalysisJob.js`    | Weekly          | Recalculates ABC classification (FR‑052).   |
| `leadTimeUpdateJob.js` | Monthly         | Computes average lead times from historical receipts (FR‑031). |
| `scheduler.js`         | Bootstrap file that initialises all jobs. |

### 8. `src/app.js`
- Creates the Express application.
- Applies global middlewares (cors, helmet, json, morgan, etc.).
- Mounts all module routes (`/api/v1/auth`, `/api/v1/stock`, etc.).
- Handles 404 and attaches the global error handler.

```javascript
// Minimal example
const express = require('express');
const cors = require('cors');
const corsOptions = require('./config/corsOptions');
const authRoutes = require('./modules/auth/auth.routes');
// ...mount all routes...
const errorHandler = require('./middleware/errorHandler');

const app = express();
app.use(cors(corsOptions));
app.use(express.json());
app.use('/api/v1/auth', authRoutes);
// ... other routes ...
app.use(errorHandler);

module.exports = app;
```

### 9. `src/server.js`
Entry point that:
1. Loads environment variables (dotenv).
2. Connects to the database (Prisma) and starts listening.
3. Initialises the MQTT client (if enabled) and the job scheduler.
4. Starts the HTTP server.

```javascript
const app = require('./app');
const prisma = require('./utils/prisma');
const mqttClient = require('./services/integration/mqttClient');
const scheduler = require('./jobs/scheduler');
const config = require('./config');

async function main() {
  await prisma.$connect();
  mqttClient.connect();   // async, non‑blocking
  scheduler.init();

  app.listen(config.PORT, () => {
    console.log(`AIMS API running on port ${config.PORT}`);
  });
}

main();
```

## Why This Structure Works for AIMS

- **Separation of concerns** – business rules live in services, not in controllers or routes.
- **Scalability** – adding a new feature (e.g., "returns") means creating a new module without touching existing code.
- **Testability** – services can be unit‑tested by mocking the Prisma client; routes and middleware can be integration‑tested with Supertest.
- **Alignment with the 90 FRs** – every functional requirement is explicitly handled by a specific module or cross‑cutting service.
- **Production‑ready** – includes scheduled jobs, external integrations, audit trail, and role‑based security from day one.

This organisation provides a clear path from the technical specification to a fully implementable, maintainable backend.
